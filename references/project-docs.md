# 网站项目文档（docs）

本 Skill 是所有网站的**基础参考**：统一的视觉、动效、交互、部署与经验沉淀规范。每个网站项目自己的 `docs/` 目录是该站的**特有参考**：记录这一个站的设计决策、实施计划与验收状态，供后续改动时先读取、后更新。

## 分层关系

- 通用、可跨项目复用的规则 → 写入本 Skill（`SKILL.md` 或 `references/`），并由 `references/lessons-learned.md` 记录来历。
- 项目专属的设计、计划与 QA → 写入该网站仓库的 `docs/`，不反向污染基础 Skill。

两类参考互补：基础 Skill 教 AI 怎么做网站，项目 `docs/` 记录"这一个站做成什么样、验收过什么、改动边界在哪"。

## 目录结构

每个网站仓库根目录下建立 `docs/`，按以下结构组织：

```text
docs/
├── specs/                   设计规格（做成什么样）
│   └── <项目>-design.md     目标、技术栈、页面与 URL、路由契约、架构职责、验收标准、后续迁移路线
├── plans/                   实施计划（怎么落地）
│   └── <项目>-plan.md       任务拆解、里程碑、关键决策与提交纪律
└── qa/                      验收与质量记录（验收到什么程度）
    └── <项目>-visual-qa.md  页面×视口矩阵、环境状态、回归结论与截图索引
```

- `<项目>` 用仓库或品牌简称，如 `mingjian`。
- `specs/` 与 `plans/` 在首次制作时建立；`qa/` 随验收推进持续更新。

## 新建网站时

1. 在 `docs/specs/` 写出设计规格：明确目标受众、技术路线、页面与路由、架构职责边界、验收标准与后续迁移路线。
2. 在 `docs/plans/` 写出实施计划：把设计拆为任务与里程碑，记录关键决策（如测试驱动、提交纪律、安全边界）。
3. 在 `docs/qa/` 建立验收基准：列出页面×视口的验收矩阵与各环境的就绪状态。
4. 把 `docs/` 整体纳入版本控制，**不加入 `.gitignore`**。注意与本 Skill 已有的"建站资料"区分：`建站资料` 是制作前的参考资料（加入 `.gitignore`，不纳入版本控制），`docs/` 是制作过程文档（纳入版本控制）。

## 更新或改版网站时

1. **先读取现有 `docs/`**：从 `specs/` 了解架构、路由契约与职责边界，从 `qa/` 拿到已验收状态与回归矩阵；任何改动都不得破坏已约定的路由规则、职责划分和已 PASS 的验收项。
2. 在既有架构约束内实施；结构性改动（新增页面、改路由、迁移数据层）需先回到 `specs/` 确认路线，避免重复造轮子或与既定方案冲突。
3. 改动完成后**更新 `docs/`**：同步 `specs/` 的变更（如新页面、新路由），并在 `qa/` 矩阵中回填本次改动的 PASS/FAIL 与回归结论。
4. 若改动中沉淀出可跨项目复用的经验，按本 Skill"反馈与经验沉淀"章节升级到基础 Skill，而非停留在单一项目的 `docs/`。

## 与工具链的衔接

若使用 Superpowers 等代理工作流，其产出的 plan / spec / qa 应直接沉淀到 `docs/` 的对应目录，避免与基础 Skill 的通用规范重复或冲突。
